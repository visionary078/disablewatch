# 看见下一步：开发与代码提交规范

**适用对象：**改硬件方案、小程序、识别网关、眼镜页、文档和测试的同事。

**目标：**硬件和软件可以同时改，又不互相覆盖、不把密钥交上去、不堆成一个看不完的大 PR。

每个小任务用一条短分支，尽早开 Draft PR。`main` 始终能集成。不要建个人长期分支，也不要建「硬件长期分支」「软件长期分支」。

产品说明和流程图在仓库根目录 [`README.md`](../README.md)。软件实现细节在 [`software/docs/看见下一步_软件技术文档_v1.7.md`](../software/docs/看见下一步_软件技术文档_v1.7.md)。聊天记录和网盘不能当唯一出处。

# 1. 仓库与 AI 入口

GitHub 仓库：[visionary078/disablewatch](https://github.com/visionary078/disablewatch)

开始开发、Review 或改文档前，先读本文件，以及任务碰到的目录说明（`hardware/README.md`、`software/README.md`）。AI 还要先读根目录 `AGENTS.md`。

AI 不会自己提交、推送或合并，除非使用者明确说了可以做哪一步。

# 2. 首次拉取和日常更新

```bash
git clone https://github.com/visionary078/disablewatch.git
cd disablewatch
git switch main
git pull --ff-only
```

识别服务的密钥从 `software/server/.env.example` 复制成 `.env` 再填。`.env` 不进仓库。

开始新任务前：

```bash
git switch main
git pull --ff-only
git status --short --branch
```

工作区里已有别人的未提交修改时，不要用 reset、clean、stash 或覆盖文件去强行更新。先弄清这些修改是谁的、跟本任务有没有关系。绕不开就停下来说明。

# 3. 每个小任务一条短分支

一条分支只做一件能单独说明、单独检查、单独 Review 的事，通常一两天内开出 Draft PR。

| 类型 | 示例 | 适用 |
|---|---|---|
| 硬件 | `feat/hardware-neckband-weight` | 方案、重量、充电、佩戴、上机检查 |
| 软件 | `feat/software-glasses-speech` | 小程序、网关、眼镜页的一块功能 |
| 修复 | `fix/infer-drop-frame` | 范围清楚的问题 |
| 文档 | `docs/commit-rules` | 说明、规范、技术文档 |
| 工程 | `chore/server-gitignore` | 依赖、忽略规则、工作流 |

```bash
git switch -c feat/software-your-small-task
```

不要用「某某的开发分支」或 `hardware` / `software` 这种一直不合并的分支。演示用已经合进 `main` 的代码。要固定某次演示，在那个提交上打 `demo-0.1` 这样的标签。

# 4. 文件放哪里

| 路径 | 放什么 | 注意 |
|---|---|---|
| `hardware/` | 眼镜方案、Word 策划案、话术、上机检查 | 不放可运行的服务代码，不放密钥 |
| `software/miniprogram/` | 微信小程序 | 用开发者工具打开这一层。`project.private.config.json` 不提交 |
| `software/server/` | FastAPI 网关、眼镜识别页、造型页、单元测试 | 模型密钥只进 `.env` |
| `software/docs/` | 软件技术文档 | 和实现不一致时，以代码和本文为准，并改文档 |
| `software/DEPLOY.md` | 部署 | 路径按现在的 `software/server` 写 |
| `README.md` | 产品设计、边界、总流程图 | 改产品口径就改这里 |
| `docs/` | 协作规范 | 本文件 |

小程序和眼镜页发给 `/infer` 的字段必须一致：`session_id`、`mode`、`spoken_text`、`distance_band`、`client`。不要在小程序和 `static/glasses/app.js` 里各写一套方向名称或风险等级。方向只允许：左、左前、正前、右前、右、未确定。

给用户听的句子里不出现米和步数。不把「可以过马路」或「可以不拿导盲杖」写进文案、提示词或接口说明。

# 5. 设计结论必须进仓库

讨论可以在聊天里进行，但聊天不进 PR，也没有版本。

- 产品边界、分层、安全口径的权威副本是根目录 `README.md`。
- 软件怎么跑通，权威副本是 `software/docs/` 里的技术文档。
- 硬件重量、充电、佩戴，权威副本是 `hardware/`。
- 合并前把结论写回这些文件。只改聊天、不改仓库，等于没改。

# 6. 提交前

1. 跑和这次改动对应的检查（见下表）。
2. 看一遍全部改动，确认没有别人的文件、密钥、本机路径、临时文件和超大参考图。
3. 只暂存这次任务负责的路径。
4. 做一个说得清的提交，推送分支，开 Draft PR。

```bash
git status --short --branch
git diff --name-status
git diff --check

git add -- path/you-own another/path/you-own
git diff --cached --name-status
git diff --cached

git commit -m "feat: describe the coherent change"
git push -u origin feat/your-small-task
```

禁止在混着别人修改的工作区里使用 `git add .`、`git add -A` 或 `git commit -am`。

禁止提交：`.env`、令牌、模型 API Key、`software/server/.venv/`、`__pycache__/`、`task_memory.sqlite`、`software/miniprogram/project.private.config.json`、造型页参考照片（`software/server/static/glasses/look/*.jpg`）。

## 提交前至少跑什么

| 改了什么 | 最少要做 |
|---|---|
| `software/server/` | 在该目录执行 `python -m unittest discover -s tests -v` |
| `software/miniprogram/` | 开发者工具里走一遍这次改的页面。没真机就在 PR 写「未在真机验证」 |
| `software/server/static/glasses/` | 浏览器打开 `/glasses/` 点开始、说一句、再看一眼。只改造型页就打开 `look.html` |
| `hardware/` 里的重量、充电、佩戴、摄像头位置 | 按 `hardware/tests/bringup-checklist.md` 填写记录。没有样机就写「未上机」 |
| 只改说明文字 | 读一遍改动的段落，确认没有把未接线的能力写成已经上线 |

没跑检查就在 PR 里写明没跑以及原因。不要写成已经验证过。

# 7. Pull Request

动手之后尽早开 Draft PR，不必等一整块做完。PR 要写：改了什么、为什么、对用户或设备有什么影响、怎么验证的、明确没做什么、要谁看。

做完后由下面的人看过，再合并进 `main`。不要直接往 `main` 推。

| 改动 | 谁必须看 | 原因 |
|---|---|---|
| `README.md` 里的产品边界：不替代手杖、不过马路、不报米数 | 项目负责人 | 全员口径 |
| 提示词、`speech` 清洗、方向和风险字段 | 项目负责人 | 说错左右或报出米数，用户无法自己核对 |
| `/infer` 的丢帧、会话锁、`session_id` | 项目负责人 | 排起队就会播几秒前的画面 |
| `model_profiles.json`、模型密钥、业务口令 | 项目负责人 | 密钥和「现在用哪个模型」 |
| 主任务 `new / keep / refine / switch` | 项目负责人 | 听完不找、或下一帧退回「前方安不安全」 |
| 小程序和眼镜页共用的请求字段 | 项目负责人 | 两边各写一套就会静默错位 |
| 脸上重量、摄像头位置、充电、磁吸脱落 | 项目负责人 | 超重或拽掉眼镜是产品红线 |
| 普通页面、文案、测试、部署说明 | 熟悉那一层的人 | 仍建议项目负责人看一眼再合并 |

项目负责人不需要看每一个提交的每一行，但每个 PR 都要经过他。上表里的改动由他亲自看。邀请同事时给 Write，不要给 Admin，避免绕过 `main` 的检查。

# 8. 让 AI 开工时可以这样说

> 请先阅读仓库根目录 AGENTS.md 和 docs/开发与代码提交规范.md，以及 README.md。只改本任务的文件，保留其他人的改动。使用短分支。不要提交 .env 和密钥。不要把未接线的双模型复核或长期记忆写成已经上线。给用户的句子不要出现米数，不要写过马路或放下导盲杖。先开 Draft PR，不要自己合并。

如果任务碰到提示词、丢帧、模型配置、主任务判定、共用字段或硬件重量，要说明这是需要项目负责人 Review 的改动。

# 9. 这份规范盖住什么

已经约定：短分支、显式暂存、Draft PR、文件放哪、设计结论进仓库、提交前检查、高风险由项目负责人看。

还没有：自动检查「这次提交有没有改出范围」。软件单元测试会在改 `software/server/` 的 PR 上跑。硬件上机检查仍然是人工的。

本规范不能代替真机。改了识别或播报，仍要听两件事：说完要找的东西后，下一帧还在找它；风险高时先听到「注意」。
